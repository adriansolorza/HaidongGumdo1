Una sola vez por computadora

Preparar la máquina

  1. Git

    Que git ignore los finales de línea de Windows (CRLF) y que el primer push de cada rama la cree en GitHub.

    git config --global user.name "Tu nombre"
git config --global user.email "tu@correo"
git config --global core.autocrlf true
git config --global push.autoSetupRemote true

  2. Flutter y Android

    Flutter estable, Android Studio con al menos un emulador, licencias aceptadas. En Windows, Modo de desarrollador encendido (los plugins necesitan enlaces simbólicos).

    flutter doctor
flutter doctor --android-licenses
start ms-settings:developers

  3. Spec Kit

    Se instala con uv. Para actualizar después, la CLI se actualiza sola.

    uv tool install specify-cli --from git+https://github.com/github/spec-kit.git
specify self check
specify self upgrade

  4. Claude Code

    En la terminal (claude) o con la extensión de VS Code. Los comandos de Spec Kit son los mismos en los dos: viven como Skills en .claude/skills/.

Una sola vez por proyecto

Arrancar el proyecto de cero

Cada paso termina en su propio commit, para que el historial cuente cómo nació el proyecto.

  1. Carpeta, git y Flutter

    mkdir C:\Proyectos\haidonggumdo
cd C:\Proyectos\haidonggumdo
git init
flutter create .
git add .
git commit -m "chore: scaffold Flutter project"

  2. Spec Kit con la integración de Claude

    Haz commit antes y después: así ves exactamente qué agregó Spec Kit.

    specify init --here --integration claude
git add .
git commit -m "chore: initialize Spec Kit with Claude integration"

  3. Repositorio en GitHub

    Crea el repositorio vacío en GitHub (sin README) y sube main.

    git remote add origin https://github.com/<usuario>/<repo>.git
git branch -M main
git push -u origin main

  4. El brief: tu intención

    docs/brief.md: qué problemas resuelve, usuarios, glosario y la tabla de ciclos (qué spec va primero). Spec Kit no lo lee solo; tú se lo pasas con @. Es tu guía y la mantienes al día.

    git add docs/brief.md
git commit -m "docs: add product brief"

  5. La constitution: tus formas

    Escribe en docs/constitution-input.md lo que no se negocia: stack, arquitectura, pruebas, qué decide la IA y qué apruebas tú. Luego, en su rama:

    git checkout -b docs/constitution
claude
    /speckit-constitution Genera la constitution del proyecto usando como entrada @docs/constitution-input.md. No agregues principios que no estén en ese archivo. Si encuentras huecos o contradicciones, pregúntame antes de escribir.

    Lee completo .specify/memory/constitution.md, haz commit (docs: ratify constitution v1.0.0), push, PR y merge a main.

  6. La spec base de la v1

    docs/000-…md: la visión completa de la versión (todas las historias, reglas y criterios). No se implementa de golpe: es el contexto que cada /speckit-specify recorta al alcance de su ciclo.

El ciclo de cada spec

Una rama por spec y un solo PR al final. Commit por cada artefacto y por cada fase, con push para tener respaldo.

A
Rama nueva

Partir de main actualizado

git checkout main
git pull origin main
git branch -d <rama-anterior>
git checkout -b NNN-nombre-corto
git push -u origin NNN-nombre-corto
claude

El número de la rama es el número de la spec (003-nivel2-evasion). Nunca uses un número que ya signifique otra spec.

- <qué queda fuera>
Reutiliza el motor sin rediseñarlo (Principio III). Hazme antes las preguntas que necesites para resolver ambigüedades. No implementes nada.

Lista de trabajo del agente

/speckit-tasks y luego /speckit-analyze

Produce:tasks.mdpor fases e historias

Tu revisión: ¿qué fases hay? ¿Cuáles tareas son manuales (tuyas)? ¿Alguna prueba existente cambia? Si cambia, que sea porque cambió lo que describe.
↺ Si analyze encuentra hallazgos: pide la corrección y vuelve a correr analyze.

Commit: docs: add tasks for spec NNN

Por fases, nunca de un jalón

/speckit-implement

/speckit-implement Ejecuta solo la Fase N (T0XX a T0YY). Detente al terminar y dime qué verificar.
Tu revisión al cerrar cada fase:
  • flutter analyze y flutter test en verde.
  • Las tareas de la fase quedaron en [X].
  • Al terminar una historia, pruébala en el emulador.
git status
git restore macos windows
git add <rutas>
git commit -m "feat: <lo que hace la fase>"
git push

Tipos de commit: feat funcionalidad, test pruebas, chore configuración y pulido, docs documentos, fix errores. El git restore descarta los archivos que Flutter regenera para macOS y Windows.

↺ Si algo no quedó bien, primero clasifícalo:
  • Bug (no hace lo que dice la spec): pide la corrección citando el requisito, por ejemplo "FR-015: con azul el símbolo sale a la derecha".
  • Cambio de idea o error de definición: corrige la spec, actualiza plan y tasks (desmarcando las afectadas), corre analyze y vuelve a implementar. Como el corte transversal de 180°.

Repite esta estación con la siguiente fase hasta terminar todas.

Lo que ya nos pasó

Cuando algo sale raro

SíntomaQué hacer
git status muestra archivos modificados que nadie tocóSolo cambiaron los finales de línea. Con core.autocrlf true ya no aparecen; si aparecen, git restore <rutas>.
"has no upstream branch" al hacer pushEs el primer push de la rama: git push -u origin <rama>.
git checkout -b dice que la rama ya existeUsa git checkout <rama> y luego git pull origin main.
El editor marca un error que flutter analyze no marcaManda la terminal. En VS Code: "Dart: Restart Analysis Server" o "Flutter: Change SDK".
Una prueba vieja falla porque la spec nueva cambió algoSe actualiza la prueba porque cambió lo que describe, y queda escrito en las tareas como cambio de datos o de presentación, no de lógica.
Aviso de "new version of Flutter"No actualices a mitad de una spec ni antes de una prueba. Hazlo entre specs, con su propio commit (Principio I).
Algo se ve mal pero "funciona"Si es funcional (no se lee, confunde), corrígelo ya. Si es estético, anótalo en el brief para la spec de experiencia visual.
Lo que aprendimos

Reglas del proyecto

La spec es la fuente de verdad

Si corriges el código y no la spec, la próxima vez que la IA lea la spec va a "corregir" tu corrección.

Spec: qué. Plan: cómo.

La tecnología y la arquitectura entran en la constitution (decisiones permanentes) y en el plan (decisiones de cada spec). Nunca en la spec.

Guarda intención, no prompts

El brief, el constitution-input y las sesiones de Clarifications guardan el porqué. Los prompts son desechables.

Datos sobre código

Patrones y niveles viven en el catálogo. Si una spec solo agrega datos y pruebas, el diseño anterior quedó bien hecho, como en la 002.

La IA propone, tú decides

Paquetes, tipografías y cambios a la constitution se proponen con pros y contras y se registran como ADR.

El conocimiento de dominio es tuyo

Dirección de los cortes, evasiones válidas, alturas: ninguna prueba automática las detecta. Revisa la spec como cinta negra.
